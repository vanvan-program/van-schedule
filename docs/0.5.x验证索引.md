## 已确认的缺口

1. **0.5.3–0.5.8 六个版本本机没有任何归档**（APK、源码包、SHA256SUMS 都没有）。tag 存在、提交存在，但 `deliverables/` 与 `GitHub上传准备/releases/` 下都找不到。要恢复只能从 GitHub Release 重新下载；若远端也未挂，则这几版的产物已不可得。
2. **0.5.0–0.5.19 共 20 个版本没有独立验证文档**。0.5.20 之前，验证结论只写在 README 段落与提交信息里。
3. **README 缺 0.5.2 一节**（0.5.3 有、0.5.2 没有）。
4. **tag 曾是手工打的**：远端（GitHub）缺 `v0.5.0`、`v0.5.1`、`v0.5.2`、`v0.5.17` 四个；`v0.5.19` 远端本来就有，只是本地副本丢了。2026-11-21 已按各自发布提交补上本地 tag（`8c02529`、`fc5421c`、`9c2d683`、`28780c2`）并推送到远端，同时补建了这四个版本的 Release，最后把 latest 标记重新指回 `v0.5.20`——GitHub 的 latest 按创建时间算，补建旧版本会把 latest 顶回旧版，导致更新器把 0.5.20 用户判成已最新。
5. **产物命名两套并存**：`deliverables/` 根目录还有旧命名 `van课表-0.3.2…0.5.2-arm64.apk`，`release-*/` 里是新命名 `van-schedule-<版本>-arm64.apk`。更新器拼直链依赖新命名，旧名只应作为历史副本。

## 关于 tag 缺口的实际影响（已于 2026-11-21 处理）

应用内更新只走 `releases/latest` 与 `releases.atom`，两者都以 GitHub Release 为准，而 Release 必须挂在 tag 上。缺 tag 的版本在远端就没有对应 Release，这些版本的用户不会收到升级提示。

现状：`v0.5.0`、`v0.5.1`、`v0.5.2`、`v0.5.17` 的 tag 与 Release 都已补齐（`v0.5.1`、`v0.5.17` 含源码包，`v0.5.0`、`v0.5.2` 当初只留了 APK 与校验文件，未补造源码包）。`releases/latest` 已确认仍指向 `v0.5.20`。

补建旧版本 Release 时有两个坑，记下来：**不能加 `--latest`**，而且 GitHub 的 latest 默认取「创建时间最新的 Release」，补完必须 `gh release edit v0.5.20 --latest` 指回去，否则更新器会把 0.5.20 用户判成已是最新。

## 今后的口径

- 先提交 `app/build.gradle` 的版本号及 `changelog.txt`、`README.md` 的版本说明，再运行 `tools/release.ps1 -Version X.Y.Z`。脚本从同一提交构建 APK、归档源码、生成 `SHA256SUMS-<版本>.txt` 并打本地标签，产物放在 `deliverables/release-<版本>/`。
- 本索引按版本追加一行；验证文档仍写 `docs/<版本>验证.md`，有就填链接。
